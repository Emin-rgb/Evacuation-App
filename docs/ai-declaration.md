## 3. How AI was used, by area

### 3.1 Planning and working agreements

- `PLAN.md` (task breakdown with a browser check per task, demo script, data to collect, decisions) and `CLAUDE.md` (stack, architecture rules, hard rules, workflow) define how the agent works. Project skills in `.claude/skills/` (backend architecture, UI style, demo polish, AI feature) hold reusable guidance the agent loads on demand.
- Rules that constrain the agent include: one task at a time and tick it off; no new dependencies without asking; do not touch files outside the task; imports through the `@/` alias; theme tokens that exist only; loading/empty/error states on every screen; commit message format; run the build before finishing.
- The agent is also configured with explicit permissions (it may not read `.env.local`, force-push or `rm -rf`).

### 3.2 Application code

Claude Code wrote the code task by task, following `PLAN.md`:

- **Database:** Drizzle schema (8 tables, enums, FKs, indexes), the re-runnable seed script with Baku districts/intersections/shelters/teams.
- **Backend:** route handlers with Zod validation, and the service layer (zone, map, shelter, routing, citizen, SOS, alert, dashboard, simulator).
- **Engine:** haversine/nearest node, Dijkstra routing with shelter selection, and the crisis detector (cluster and overload rules).
- **Frontend:** app shell, citizen view, dispatcher view, SVG city map, simulator panel, SOS dialog, alert cards, skeleton/empty/error states.

### 3.3 Tests

The 31 engine unit tests (`tests/geo.test.ts`, `tests/routing.test.ts`, `tests/crisis.test.ts`) were written by the agent from the acceptance criteria in task 13 (Dijkstra avoids closed edges, route skips shelters ≥90%, cluster rules, overload rule, de-duplication). They run with `npm test`.

### 3.4 Architecture

The layered structure (UI → API route → service → engine/provider → DB), the choice of a pure DB-free engine, and the `TrafficProvider` interface were proposed in the planning session with the agent and then **decided by the team**. The decisions and rejected alternatives are recorded in `PLAN.md` (Decisions) and `docs/technical.md` (section 12).

### 3.5 Documentation

`README.md`, `docs/technical.md` and this file were drafted by the agent by reading the actual source code and the git history, then checked against the code. During that check the agent corrected its own draft where it over-claimed (for example, the citizen map is not polled, only the route is).

## 4. How we kept control (human in the loop)

- **Small, reviewable steps.** One task per commit, each with a defined acceptance check (a browser step or `npm test`); a task is only ticked off in `PLAN.md` after its check passes.
- **Decisions are ours.** Scope, stack, the "NOT building" list, the alert thresholds (4 SOS / 500 m / 5 min, 95% overload, 90% reroute) and the demo script come from the team and the case, not from the agent.
- **Constraints enforced in writing.** `CLAUDE.md` forbids new dependencies and out-of-scope edits, so the agent's changes stay inside the task.
- **Build gate.** `npm run build` (type-check) is run before a task is finished.
- **History is auditable.** Every change is a commit with a conventional message.

## 5. Known limits of AI assistance in this project

- AI-generated code can contain mistakes; only the engine has automated tests. The rest was verified by manual browser checks against the demo script.
- The seed coordinates for intersections and shelters are **approximate**, produced by the agent from general knowledge of Baku, not surveyed data. They are suitable for a schematic demo, not for real navigation.
- The seed data (shelter capacities, occupancy, team names) is **fictional**.

## 6. Not used

- No AI/LLM feature exists in the product; no model is called at runtime and no API key for one is required (`GEMINI_API_KEY` in `.env.example` is unused).
- No AI-generated images, audio or third-party datasets are included.
